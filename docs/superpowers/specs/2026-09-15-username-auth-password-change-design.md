# Username Authentication and Password Change Design

## Goal

Replace the admin login identifier from e-mail to a globally unique username, preserve Supabase Auth as the underlying identity provider, add automatic username availability feedback when configuring employee access, and add a self-service password-change flow on the login screen.

## Scope

This change covers:

- globally unique usernames for system users;
- migration of existing users without interrupting access;
- employee access creation/editing using username instead of login e-mail;
- automatic username availability feedback while editing access;
- admin login with username + password;
- password change from the login screen using username + current password + new password + confirmation;
- password visibility controls using the existing eye/eye-off interaction;
- checklist toolbar badge becoming green only when the checklist is actually completed.

It does not change registration contact e-mail fields, organization membership rules, role/permission semantics, or the multi-company isolation model.

## Username Rules

`profiles.username` is the canonical login identifier.

- Global uniqueness across all organizations.
- Case-insensitive; values are stored normalized to lowercase.
- Allowed characters: lowercase ASCII letters, digits, `.`, `_`, and `-`.
- Length: 3 to 32 characters.
- Username is independent from display name, employee name, contact e-mail, organization and role.
- Two people may have the same name, but two system users may not have the same username.

The database is the final authority for uniqueness. UI availability checks are advisory and must never replace the unique database constraint.

## Existing User Migration

Existing profiles receive an initial username derived from the local part of their current Auth/profile e-mail. Production was checked before implementation: all current profiles have e-mail, current local parts are valid under the username rule, and no duplicate local parts exist.

The migration remains deterministic and defensive for non-production environments by normalizing candidate usernames and adding a short suffix only if a collision exists there.

Existing Supabase Auth e-mails remain valid internal identity fields. Users will no longer need to know or type them to sign in.

## Authentication Architecture

Supabase `signInWithPassword` requires an e-mail or phone number. The browser therefore must not translate username to e-mail by directly querying profiles.

A public Edge Function dedicated to username authentication performs the translation server-side using the service role and exposes no profile details. It supports:

1. `login`
   - normalize username;
   - resolve exactly one active profile;
   - resolve its internal Auth e-mail;
   - authenticate that e-mail and supplied password using the anon Auth client;
   - reject inactive users;
   - return only the session tokens required by the browser;
   - the browser installs the returned session with `supabase.auth.setSession`.

2. `change_password`
   - normalize username;
   - resolve profile and internal Auth e-mail;
   - authenticate the supplied current password first;
   - validate the new password;
   - update the same Auth user through the admin client;
   - return a generic success/error response without leaking account details.

Login failures use generic invalid-credential messages so the endpoint does not become an account-enumeration API.

The function intentionally runs without JWT verification because login and pre-login password change occur before a user session exists. It implements its own credential validation.

## Employee Access Creation / Editing

The access form stops asking for a login e-mail and asks for `Usuário` instead.

For new access:

- username is required;
- password is required and keeps the existing minimum of 8 characters;
- role remains required;
- an internal synthetic Auth e-mail is generated by the server from the globally unique username, while the employee's contact e-mail remains separate;
- the synthetic/internal e-mail is never displayed as the login identifier.

For existing access:

- current username is loaded from `profiles.username`;
- changing username updates only `profiles.username`; it does not need to change the existing internal Auth e-mail;
- leaving the password blank keeps the current password;
- existing activation, role and Uniq logic remains unchanged.

## Username Availability Check

While the access form is enabled and the username is syntactically valid, the UI performs a debounced availability check.

The existing authenticated `employee-access` Edge Function receives a `check_username` action. It:

- requires an authenticated caller;
- validates the organization/employee context and view/create/edit permissions;
- normalizes the username;
- checks `profiles.username` globally;
- treats the current employee's own username as available when editing;
- returns only `{ available: boolean, username: normalizedUsername }`.

The UI states are:

- neutral/instructional before a valid value is present;
- checking;
- green `Usuário disponível`;
- red `Usuário já está em uso`;
- validation error for invalid syntax.

Saving is blocked when a new/changed enabled username is not confirmed available. The database unique constraint still protects against race conditions between check and save.

## Login UI

The current `AdminLogin` visual design is retained.

Default mode:

- field: `Usuário`;
- field: `Senha`;
- existing password visibility eye;
- primary `Entrar` button;
- secondary text action `Alterar senha`.

Password-change mode, in the same login surface:

- `Usuário`;
- `Senha atual`;
- `Nova senha`;
- `Confirmar nova senha`;
- each password field has the same eye/eye-off control pattern already used by the login;
- primary `Alterar senha` button;
- secondary `Voltar para o login` action.

On success, the screen returns to normal login mode with the username preserved and a success message.

## Checklist Toolbar Badge

`OrderChecklistToolbarButton` keeps the current progress fraction. The badge is blue while the checklist is pending/in progress. It becomes green only when `query.data.status === "completed"`.

This deliberately does not infer completion from `answered === total`, because photos, observations and stage completion rules may still be pending.

## Security / Multi-company Notes

- Username is global, therefore the login screen does not need to ask for company.
- Organization access is still determined after authentication through existing memberships and permissions.
- No public table policy is added to expose usernames, e-mails or organizations.
- Availability checks reveal only whether a candidate username is available, which is an explicit product requirement.
- Login errors remain generic.
- Database uniqueness is authoritative; UI checks are convenience only.
